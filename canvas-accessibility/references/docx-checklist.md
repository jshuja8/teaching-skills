# Word (.docx) accessibility: what to check and how to fix it

Run `scripts/check_docx_accessibility.py <file>` first for a deterministic report,
then fix issues directly in the XML (with the `docx` skill's unzip → edit →
validate → rezip workflow if that skill is available, or through
python-docx/lxml if not; see SKILL.md Step 2). All fixes below preserve
visual appearance because Word lets a style (like `Heading2`) coexist with
direct run formatting (bold, color, size) on the same paragraph — the direct
formatting still wins, so applying a heading style never changes how the
document looks, only what a screen reader announces it as.

## 1. Heading structure

**Why it matters:** Screen reader users navigate long documents by jumping
between headings (like sighted users skim with their eyes). Bold, large, or
colored text that isn't tagged with a Heading style is invisible to that
navigation — it reads as plain paragraph text.

**How to check:** Does any paragraph use `Heading1`–`Heading6` or `Title` as
its `w:pStyle`? If the document has real section structure (a title, then
distinct sections) and none of it is tagged, that's the issue.

**A subtler version of the same issue: the document's own title/subtitle
left untagged while everything below it IS tagged.** A worksheet whose eight
section headers all correctly use `Heading 2`, but whose title line at the
very top is still plain bold text with no style, still fails — and it's easy
to miss because the checker's "no heading structure at all" test passes (some
headings exist). Explicitly check what level the *first* heading in the
document is. If real content structure starts at `Heading 2` (or deeper) with
no `Title` or `Heading 1` above it, that's a skipped level at the very top —
the fix is the same as any other heading fix (add `Title` to the document
name, `Heading 1` to a subtitle line if there is one), it's just easy to
overlook since the rest of the document already looks "done."

**How to fix:** Insert `<w:pStyle w:val="HeadingN"/>` (or `Title`) as the
*first* child of the paragraph's `<w:pPr>`. Use the paraId to target the
specific paragraph precisely:

```xml
<w:p w14:paraId="XXXX" ...><w:pPr><w:pStyle w:val="Heading2"/>...existing pPr children...</w:pPr>...
```

**If the document has no `w14:paraId` attributes at all** (common in files
generated by tools other than Word itself — python-docx, docx-js, Google
Docs export, etc.), don't try to anchor edits by paraId; edit via
python-docx's object model instead (`paragraph.style`, or set
`w:pStyle` directly via `OxmlElement`/`qn` on `paragraph._p.get_or_add_pPr()`
for full control). Note also that `doc.styles['Style Name']` can raise a
`KeyError` even when the style visibly exists (a `BabelFish`
name-normalization mismatch on certain style definitions) — if that happens,
skip the name-based lookup and set `w:pStyle`'s `w:val` directly to the
style's `w:styleId` (e.g. `"Heading1"`, not `"Heading 1"`), which always
works regardless of the style's declared display name.

Map heading levels to the document's actual structure — don't skip levels
(e.g. don't jump from Title straight to Heading3, and don't start the
document's structure at Heading2 with nothing above it). A typical worksheet
or handout needs: `Title` (document name) → `Heading1` (major sections, or a
subtitle line) → `Heading2` (subsections/activities). Check `word/styles.xml`
first — if `Heading1`/`Heading2`/etc. don't exist as styles, they need to be
added (rare; most templates have them already, sometimes hidden/semiHidden
which is fine).

## 2. Table header rows

**Why it matters:** Without a marked header row, a screen reader reads every
cell as anonymous data — it can't announce "Statement" before reading cell
content, so column meaning is lost, especially in tables that scroll or break
across pages.

**How to check:** For each `<w:tbl>` with more than one row AND more than one
column, does the first `<w:tr>` have `<w:trPr><w:tblHeader/></w:trPr>`?
Single-cell tables used as blank drawing/writing space (common in activity
worksheets) don't need this — there's no header/data distinction to make.

**Critical: "multi-row, multi-column" is necessary but not sufficient — read
the actual content before marking a header row.** The checker script flags
any multi-row, multi-column table as a *candidate*, but plenty of tables that
shape doesn't have a real header row at all. The test that matters: **does
row 1's content apply, unchanged, to every row below it in that column?**

- `Kitchen concept | Computer concept` followed by rows of matched pairs —
  yes, "Kitchen concept" genuinely describes every left-hand cell below it.
  **This is a real header row.**
- `Top | Users`, then blank/`Applications`, then blank/blank, then
  `Bottom | ...` — "Top" does **not** describe the left-hand cell of every
  row below it (row 2's left cell is blank, row 4's is "Bottom"). This is a
  positional/labeled-diagram table, not a header+data table, even though it
  has multiple rows and columns. **Marking this as a header row is wrong** —
  a screen reader would announce "Top" before every subsequent row's first
  cell, actively misdescribing the layout.
- A table where every row is an independent `label: blank-for-answer` pair
  (an exit-ticket table, a term-matching table with no column-label row) has
  **no header row to mark at all** — don't invent one by relabeling existing
  content, since that changes what the document says. Alt text is the right
  (and only) fix for these.

Word also has no equivalent to HTML's `scope="row"` — there's no clean way
to mark "Top"/"Bottom" as *row* headers the way `tblHeader` marks *column*
headers. When a table would genuinely benefit from row headers but Word
can't express that, say so in the summary rather than working around it with
a technically-wrong column header.

**How to fix (when it IS a real header row):** Add
`<w:trPr><w:tblHeader/></w:trPr>` as the first child of the header `<w:tr>`
element. This also makes the row repeat automatically if the table spans a
page break, which is a nice side effect.

## 3. Table alt text

**Why it matters:** Word's accessibility checker (and Canvas's) flags any
table without a title/description in Table Properties > Alt Text. A screen
reader announces this before reading the table, giving context — including
for tables with no real header row (blank sketch boxes, label/blank-answer
tables, positional diagrams), where the description should explain the
table's *layout and purpose* since there's no header row doing that job.

**How to fix:** Add `tblCaption` (short title) and `tblDescription` (one to
two sentences) inside `<w:tblPr>`. **Order matters** — per the OOXML schema,
these must come near the *end* of `tblPr`'s children, after `tblLook`, not
right after `tblW`:

```xml
<w:tblPr>
  <w:tblW .../>
  ...tblBorders, tblCellMar, tblLook, etc...
  <w:tblCaption w:val="Short title"/>
  <w:tblDescription w:val="One or two sentences describing the table's purpose and layout."/>
</w:tblPr>
```

If editing via python-docx/lxml rather than raw string ops, you can simply
`.append()` these two elements to the end of the existing `tblPr` element —
since they're always last in the schema sequence, appending is always valid
regardless of what other children already exist. Either way, validate
afterwards (the docx skill's `validate.py` if available, otherwise re-open
and render the file) — putting them in the wrong position won't necessarily
break rendering in Word, but it will fail strict schema validation.

## 4. Image alt text

**Why it matters:** A screen reader can't describe an image it has no text
for. An empty or missing `descr` reads as just "image" or the filename.

**How to check:** For each `<wp:docPr>` (inline or anchored drawing), is
`descr` (or `title`) non-empty, OR is it marked decorative (an `extLst` entry
containing `decorative`)? Purely ornamental images (borders, dividers) should
be marked decorative rather than given a fake description.

**How to fix:** Set `descr="..."` on the `<wp:docPr>` element with a concise,
specific description of what the image conveys (not "image of..." — just
describe it, e.g. "Sequence diagram showing Member requesting a book from the
Librarian").

## 5. Hyperlink text

**Why it matters:** Screen reader users often pull up a list of all links on
a page and scan it out of context. "Click here" or "here" repeated multiple
times is meaningless in that view.

**How to fix:** Replace the visible run text inside `<w:hyperlink>` with
something that describes the destination, e.g. "Week 1 syllabus (PDF)"
instead of "click here".

## 6. Document title (metadata)

**Why it matters:** Canvas and screen readers show the file's Title property
(in `docProps/core.xml`, the `<dc:title>` element) instead of the raw
filename when it's set. Leaving it blank means students hear
"CS445_W1_Worksheet_v3_FINAL.docx" instead of a readable name.

**How to fix:** Set `doc.core_properties.title` (python-docx) or edit
`<dc:title>` directly in `docProps/core.xml`. Use a human-readable title
matching what you'd want announced, not the filename.

## 7. Default document language

**Why it matters:** Without a language tag, screen readers guess
pronunciation rules, which can badly mangle text (especially non-English
words, names, or technical terms).

**How to fix — and a trap to avoid:** `doc.core_properties.language` sets
the Dublin Core `dc:language` metadata in `docProps/core.xml`. That's
descriptive metadata only — it is **not** what controls pronunciation.
The setting that actually matters is `<w:lang w:val="en-US"/>` inside
`word/styles.xml`'s `<w:docDefaults><w:rPrDefault><w:rPr>`. Set both: the
core property because Canvas/some checkers do look for it, and the
docDefaults `w:lang` because that's what assistive technology actually
uses. If `rPrDefault` is present but empty (`<w:rPrDefault/>`), you need to
add the `<w:rPr><w:lang .../></w:rPr>` inside it — don't assume setting the
core property alone is sufficient, and re-run the checker script afterward
to confirm the language check actually passes (it checks docDefaults, not
core properties, precisely because that's the one that matters).

## What this checklist does NOT catch

Some accessibility issues need human judgment and aren't worth trying to
detect automatically — mention these to the instructor rather than silently
skipping them:
- **Color-only meaning** (e.g., "red rows are overdue" with no other cue).
- **Reading order** in documents with text boxes or floating elements — docx
  reading order is mostly determined by document order, so this is a much
  smaller risk here than in PowerPoint or complex layouts, but worth a glance
  if the doc has floating text boxes.
- **Whether an image's alt text is actually accurate** — the script can only
  tell you alt text is present/absent, not whether it's correct.
